# 印刷キュー

保存済みのプレートを順番に印刷します。次の印刷を開始するには、利用者が造形物を取り外し、
ビルドプレートを戻してから操作します。完了通知だけで次の印刷を始めることはありません。
ブラウザのメニューから「印刷キュー」を開くか、`/queue`へアクセスします。

キューはメモリに保持し、サーバー再起動で消えます。保存済みプレートは残ります。
プリンターの[接続設定](printer.md#接続設定)と、[スライス済みプレート](slicing.md)を用意してください。
プリンター未接続でもキューへ追加できますが、同期済みの待機状態になるまで印刷は開始できません。

## 画面から操作する

1. 保存済みプレートの詳細で「印刷キューへ」を開きます。
2. プリンターと使用するAMSスロットを選び、「キューに追加」を押します。画面は1始まりのユニット・スロットと材料を表示します。
3. 待機行の「前へ」「後へ」で順番を変え、「削除」で待機から外せます。
4. 造形物を取り外して空のビルドプレートを戻し、確認欄をチェックして「次を印刷」を押します。
5. 完了後も同じ内容を確認して次を開始します。最後のジョブは「取り外しを完了」で閉じます。

状態が変わった場合、確認欄をチェックし直します。送信結果が不明なら「同じ要求を再確認」で確認できます。
別の端末が操作していた場合は、更新された内容を確認して操作し直してください。
失敗時は表示された理由と本体を確認します。「同じプレートを再印刷」または「現在のジョブを除く」を選べます。
これらは印刷停止命令ではありません。印刷が続いている場合は本体と接続を確認し、復帰を待ちます。

以下は、HTTPクライアントや近傍ボタンの送信装置を設定する人向けのAPIです。

キューは機器ごとに独立しています。APIでは`?printer_id=PRINTER_ID`を全てのGET/POSTに付けます。
IDは`GET /api/printers`から取得します。登録が1台だけなら省略できますが、複数台の場合は409です。
指定IDが不明な場合、別の機器へ振り替えることはありません。

## APIでプレートを追加する

`GET /api/plates`でプレートの`id`と`revision`を、`GET /api/queue`で現在の`generation`と`request_id`を取得します。
以下の`PLATE_ID`、`REVISION`、`REQUEST_UUID`を実際の値に置き換えます。
`generation`には直前のキュー応答の値を使います。例の0は起動直後の空のキューに対応します。

```sh
curl --fail-with-body -X POST http://127.0.0.1:3000/api/queue \
  -H 'Content-Type: application/json' \
  -d '{"generation":0,"request_id":"REQUEST_UUID","action":{"type":"add","plate_id":"PLATE_ID","revision":"REVISION","ams_slot":3}}'
```

`ams_slot`は0〜15で、`AMS unit × 4 + tray`です。例の3は最初のAMSの4番目のトレイです。
印刷開始時に、トレイの在席と材料種別を確認します。

追加時のモデル、設定、編集用3MF、印刷3MF、AMS選択をジョブへ固定します。
その後に元のプレートを編集したりSTLを更新したりしても、投入済みジョブは変わりません。
変更を反映する場合は待機ジョブを削除して追加し直します。

## 最初と次の印刷

1. `GET /api/queue`で最新の`generation`と`waiting[0].id`を取得します。
2. 造形物を除去し、ビルドプレートを戻します。最初の印刷でもプレートが空であることを確認します。
3. `expected_job`にその先頭ID、`cleared:true`を指定して`next`を送ります。
4. `current.phase`が`awaiting_removal`になったら、次の印刷に向けて同じ操作を繰り返します。

```json
{
  "generation": 1,
  "request_id": "REQUEST_UUID",
  "action": {"type": "next", "expected_job": "WAITING_JOB_ID", "cleared": true}
}
```

数字とIDは取得した値へ置き換えます。二重押下や別クライアントとの同時操作でも、同じ世代から2件を開始しません。
スマホのHTTPクライアントや物理ボタン側も、この取得・確認・送信の契約を使えます。
同時操作で409になった場合、期待するジョブを自動で次のIDへ差し替えて再送しないでください。

### 近傍ボタンやHTTP送信装置

ボタンを押す人が造形物と空のビルドプレートを確認してから、送信装置が最新のキューを取得します。
その応答の`generation`・`request_id`・`waiting[0].id`で上のJSONを作り、1回の押下に対応する要求として保持します。
同じボタンの再送で別の先頭IDを取り直すことは避けてください。

curlで同じ要求を送る場合は、作成したJSONを`next.json`へ保存して実行します。
接続先は利用中のサーバーへ置き換えます。

```sh
curl --fail-with-body http://127.0.0.1:3000/api/queue \
  -H 'Content-Type: application/json' --data-binary @next.json
```

応答が届かなければ同じファイルで再送できます。200でも次を自動で開始せず、現在の状態を表示します。
409なら自動再送を止め、画面で対象と状態を確認してから新しい操作を準備します。
再起動で消えたジョブの要求も、新しい先頭に差し替えて再送しません。

## 状態を取得する

```sh
curl --fail http://127.0.0.1:3000/api/queue
```

| 項目 | 内容 |
| --- | --- |
| `request_id` | この応答を基に行う操作に使えるUUID。応答ごとに新しく発行します。 |
| `allowed` | `next`・`retry`・`discard`の実行可否。取り外し確認を済ませた場合の表示用判定で、POST時にも条件を再確認します。 |
| `generation` | キューの版を示す整数。変更・進行状態の更新で変わります。 |
| `waiting` | 待機中のジョブ。先頭が次の印刷です。最大100件。 |
| `current` | 現在のジョブ。ない場合は`null`。`job`、`phase`、`attempt_id`、`message`を持ちます。 |
| `printer` | [プリンター状態](printer.md#状態api)。開始条件と詳細な進行状況を確認できます。 |

ジョブは`id`、`plate_id`、`revision`、`name`、`ams_slot`を持ちます。
`id`はキュー内のジョブIDです。同じプレートを複数回追加すると、それぞれ別のIDになります。

| `current.phase` | 意味 |
| --- | --- |
| `starting` | 転送または開始確認を待っています。 |
| `printing` | 対象ジョブの印刷中です。 |
| `awaiting_removal` | 完了を確認しました。造形物の取り外しとプレートの再セットを待っています。 |
| `needs_attention` | 転送失敗・中止・一時停止・通信断など。端末を確認して復旧操作を選びます。 |

## 操作の共通形式

すべての変更は`POST /api/queue`へ、上の例と同じ`generation`、`request_id`、`action`を送ります。
`request_id`には直前の応答にあるUUID、または操作ごとに用意した新しいUUIDを使います。応答を受け取れなかった場合だけ、同じ入力で再送できます。
直前に受理した同一要求の再送は現在の状態を返し、操作を繰り返しません。
別の操作を挟んだ古い要求や、同じIDで内容を変えた要求は409です。

| `action.type` | 追加で必要な項目と操作 |
| --- | --- |
| `add` | `plate_id`、`revision`、`ams_slot`。末尾へ追加。 |
| `move` | `job_id`、`index`。待機ジョブを0始まりの位置へ移動。 |
| `remove` | `job_id`。待機ジョブを削除。印刷中のジョブは削除できません。 |
| `next` | `expected_job`、`cleared:true`。期待する先頭ジョブを1件開始。 |
| `retry` | `expected_job`、`cleared:true`。確認済みの`needs_attention`ジョブを同じ内容で再実行。 |
| `discard` | `expected_job`、`cleared:true`。確認済みの現在ジョブを除去。次の印刷は始めません。 |

成功は200と最新の状態を返します。印刷開始の成功は`printer.start`と`current.phase`で確認してください。
世代・対象ジョブ・状態が合わない場合は409です。最新状態を取得し、意図した対象を確認して操作し直します。
入力不正は400または422、存在しないプレートは404です。ブラウザからの別Originの変更要求は403です。

## 失敗や中止からの復旧

`needs_attention`では`message`とプリンター本体を確認します。
印刷が継続中なら再実行せず、通信や一時停止を解消して報告の復帰を待ってください。
対象の印刷報告が戻れば、状態へ反映します。

再実行する場合は端末の結果を確認し、造形物を除去してプレートを戻した後に`retry`を使います。
不要になった現在ジョブは`discard`で除去できます。どちらも同期済みの待機状態と`cleared:true`が必要です。
`expected_job`には`current.job.id`を指定します。これは待機行列の先頭IDとは異なります。
これらの操作は印刷停止命令を送りません。本体で停止した場合も、完了扱いで次へ進めません。

ジョブのファイルはOSの一時領域へ複製し、削除・次への移動・通常終了で片付けます。
異常終了時に残った一時ファイルからキューを復元することはありません。
再起動後はキューが空になり、プリンターの新しい全状態を確認してから操作します。
